# Reflexão Crítica

### 1. As regras de transição de estado são o coração do domínio, mas o contrato só as refere em texto, nas `description` dos `409`. Isso chega a quem escreve o cliente? E a quem escreve o servidor?

A documentação baseada apenas em texto nas descrições dos erros `409 Conflict` revela-se insuficiente para ambas as partes. Para o desenvolvimento do cliente, a ausência de uma definição formal das transições de estado impossibilita o conhecimento prévio e programático das regras de negócio (por exemplo, a impossibilidade de transitar diretamente de `submetida` para `resolvida`). Para o servidor, o contrato não fornece o rigor necessário para a implementação das validações de estado. A especificação OpenAPI descreve a sintaxe e a estrutura dos dados com precisão, mas a semântica das regras de negócio e o controlo das transições de estado não podem ser delegados ao contrato; devem ser garantidos e programados ao nível da lógica aplicacional no backend.

### 2. A listagem devolve o `numeroAluno` de todas as sugestões. É um problema? O contrato de base consegue exprimir «visível só para o autor»?

A devolução indiscriminada do `numeroAluno` na listagem geral constitui um risco de privacidade, expondo dados pessoais indevidamente a terceiros. O contrato OpenAPI, na sua conceção estrutural base, define o modelo de dados (através do schema `Sugestao`), mas carece de semântica para exprimir regras de autorização granulares ao nível do registo (Row-Level Security), como a condição "visível apenas para o autor". A resolução desta vulnerabilidade exige a implementação de lógicas de controlo de acesso dinâmico no servidor. Do ponto de vista da modelação do contrato, exigiria a separação em representações distintas: um schema público (excluindo dados sensíveis) e um schema privado (reservado ao autor ou a administradores devidamente autenticados).

### 3. Com `max-age=3600`, um cliente pode ver estatísticas com quase duas horas de atraso face aos dados reais. Quem ganha e quem perde com essa escolha? O que mudaria com `no-cache`?

A diretiva `public, max-age=3600` estabelece que a resposta pode ser armazenada e reutilizada por qualquer cache durante uma hora. Esta decisão arquitetual beneficia o servidor e a infraestrutura de rede (redução drástica da carga computacional, das consultas à base de dados e do tráfego) e o cliente (menor latência na obtenção da resposta). Em contrapartida, prejudica os utilizadores e analistas que dependam de rigor em tempo real, sujeitando-os a consumir informação desatualizada durante a janela de validade da cache. A substituição por `no-cache` não proíbe o armazenamento, mas obriga as caches a revalidar o estado do recurso com o servidor (utilizando o cabeçalho `If-None-Match`) antes de cada utilização. Isto garantiria a consistência contínua da informação, penalizando, contudo, o tempo de resposta e o volume de tráfego caso os dados sofram atualizações muito frequentes.

### 4. A versão `v1` está no URL base. Amanhã acrescenta-se à `SugestaoNova` uma propriedade obrigatória nova. O que acontece aos clientes existentes? E se a propriedade nova fosse acrescentada, obrigatória, apenas a `Sugestao`? Qual das duas alterações obriga a uma `v2`?

A introdução de uma nova propriedade obrigatória no schema `SugestaoNova` (modelo de input) configura uma *breaking change*. Os clientes existentes, cujos pedidos não incluam essa nova propriedade, verão as suas submissões sumariamente rejeitadas pelo servidor com o código `400 Bad Request`. Esta quebra de retrocompatibilidade exige obrigatoriamente a transição para uma nova versão da API (`v2`). Inversamente, a adição de uma propriedade exclusiva ao schema de resposta `Sugestao` (output) preserva a retrocompatibilidade. Por norma, os clientes ignoram campos desconhecidos contidos no payload recebido, permitindo que a API continue a operar sob a versão `v1` sem disrupção do ecossistema existente.

### 5. A especificação está em YAML, mas a API troca JSON. Porque é que isso não é uma contradição? O que é que o YAML descreve, e o que é que o JSON transporta?

Não existe contradição, pois cumprem propósitos tecnológicos distintos no ciclo de vida da aplicação. O YAML opera como a linguagem de desenho e documentação técnica (o contrato); a sua sintaxe estruturada por indentação e o suporte nativo a comentários tornam-no na escolha ideal para o planeamento e leitura humana. O JSON, por sua vez, atua como o formato de transporte de dados *standard* utilizado na comunicação HTTP entre o cliente e o servidor. Conclui-se que o YAML descreve estaticamente a arquitetura, as validações e as regras da API, ao passo que o JSON materializa dinamicamente essa estrutura, transportando a informação útil durante o tempo de execução.

### 6. Compare o custo de escrever o contrato antes do código com o custo de o descobrir depois, na integração: que desacordos entre cliente e servidor passam a ser detetados no momento certo?

A adoção de uma abordagem *Design-First* (redigir o contrato OpenAPI antes da implementação) exige um esforço inicial de planeamento, mas elimina os custos exponenciais associados a falhas de integração tardias. Quando o contrato é definido apenas *a posteriori* (ou assumido tacitamente), divergências estruturais cruciais — tais como tipagem incorreta, ausência de parâmetros obrigatórios, disparidade nos códigos HTTP ou falta de cabeçalhos de concorrência — apenas são detetadas quando as componentes de frontend e backend já se encontram desenvolvidas. Esta deteção tardia resulta em refatorizações morosas. A elaboração prévia do contrato cria um documento normativo inambíguo, permitindo o desenvolvimento concorrente das equipas e estabelecendo validações estritas (ex: limites, formatos, obrigatoriedades) desde o primeiro momento.
